# US-02 test matrix: risk rule management

This matrix describes the current test baseline. All API operations require an active user in the `manager` group. `AMOUNT_LIMIT` requires an integer `max_amount` between 1 and `2^63-1`. Each successful service write records the revision and history in one transaction.

| ID | Scenario | Input | Expected result | Coverage |
|---|---|---|---|---|
| R02-01 | Valid creation | Amount 1 or `2^63-1` | Success, revision 1, and one history record | Unit and integration: `test_valid_amount_boundaries`, `test_valid_boundaries` |
| R02-02 | Invalid boundary | 0, negative, `2^63`, decimal, boolean, or missing amount | 400 or validation error; no new data | `test_invalid_parameters_rejected_without_side_effects`, `test_invalid_amount_parameters_do_not_create_rule_or_history` |
| R02-03 | Parameter format | Array or null | Validation error | Invalid input tests above |
| R02-04 | Valid update | Current revision and new amount | 200, incremented revision, and before/after snapshots and actor recorded | `test_create_update_and_read_audit` |
| R02-05 | Concurrent users | Stale expected revision | 409 without changes or new history | `test_stale_and_invalid_patch_leave_original_unchanged` |
| R02-06 | Invalid update | Invalid value or actor in body | 400; state remains unchanged | Same test as R02-05 |
| R02-07 | Creation retry | Same key and body | Same 201 and response; only one rule and history record | `test_post_replay_and_conflict` |
| R02-08 | Key reuse | Same key with different body or user | 409 `IDEMPOTENCY_KEY_REUSED`; prior response is not disclosed | `test_post_replay_and_conflict`, `test_same_key_cannot_leak_response_to_another_manager` |
| R02-09 | Authentication and authorization | Missing JWT or manager group | 401 and 403 respectively | `test_auth_and_missing_rule`, `test_non_managers_are_denied` |
| R02-10 | Unknown rule | Unknown UUID | 404 for update and history | `test_auth_and_missing_rule` |
| R02-11 | History pagination | limit=1 and cursor | Revisions in descending order without duplicates | `test_audit_cursor_pages` |
| R02-12 | History write failure | Error recording history | Rule update rolls back | `test_history_failure_rolls_back_existing_rule_update` |
| R02-13 | Direct PostgreSQL history modification | UPDATE or DELETE | Database error | `test_database_rejects_history_update_and_delete` |
| R02-14 | Legacy rule without history | Update an existing rule at revision 3 | Only revision 4 and its before/after snapshots are recorded | `test_existing_rule_gets_history_only_when_updated` |
| R02-15 | Concurrent requests | Two POST requests with the same key | Two identical responses and one rule | `test_concurrent_post_same_key_creates_one_rule` |
| R02-16 | Concurrent edits | Both use the same revision | One 200 and one 409; only one new revision | `test_concurrent_patch_allows_only_one_revision` |

Limitation: direct ORM or SQL writes to RiskRule can bypass the service. The history trigger prevents ordinary UPDATE/DELETE operations, but the database owner can disable it and TRUNCATE is not protected; separate roles and permissions are required for production deployment.
